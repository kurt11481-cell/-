## Confirmed v2.3 defects and gaps

1. No provider-agnostic independent completed-close adapter or one-shot provider preflight exists. A provider-wide outage is repeated as ticker-level failures.
2. Radar treats any partial candidate-data result as a global `DATA_INCOMPLETE` conclusion, even when an unrelated validated candidate remains usable for research.
3. Hard-risk records do not expose rule-level provenance, approval status, `action_on_breach`, primary-close status, or independent-close status. The holding strategy currently maps every grade-D breach directly to `EXIT_REVIEW`.
4. Risk State and Strategy State are not independently modeled.
5. Cash verification accepts a numeric value plus `cash_verified`; it does not require verified/complete/fresh broker state or strategy-version consistency.
6. Verified zero cash incorrectly selects `KEEP_CASH` as the preferred capital use.
7. A held Radar ticker can appear as `NEW_POSITION` and again as `EXISTING_HOLDING_ADD`.
8. No immutable post-market baseline or bounded pre-open delta-refresh contract exists.
9. Runtime events and dedup keys do not identify `POST_MARKET` versus `PRE_OPEN`.
10. Automation configuration and successful delivery are not represented as separate lifecycle states.

## Planned implementation

### Data reliability and failure scoping

- Add a capability-driven independent completed-close snapshot builder, validator, and provider preflight.
- Preserve source provenance and reject Yahoo-origin data as an independent cross-check.
- Model provider-wide failure separately from ticker-specific failure.
- Aggregate provider-wide incidents into one global transition/notification.
- Permit partial-domain Radar research when at least one candidate remains valid, without weakening ticker-level fail-closed behavior.

### Hard-risk provenance and state separation

- Add a deterministic hard-risk policy audit and an auditable artifact.
- Preserve the approved SOXL, MVLL, and NBIS loss fractions; add only evidence-backed provenance and explicit authority status.
- Introduce independent Holding Risk State and Holding Strategy State fields.
- Map a breach to strategy only through verified `action_on_breach`; otherwise require strategy refresh and human review.
- Expose primary close, independent close, policy authority, quantity authority, and price verification independently.

### Cash and capital redeployment

- Add a single deterministic cash-status evaluation with freshness, completeness, verification, settlement, and strategy-version checks.
- Use only `VERIFIED_POSITIVE` as execution purchasing power.
- Return `NO_FUNDED_ACTION`, null preferred/alternative use, and `NOT_APPLICABLE` keep-cash semantics for verified zero cash.
- Keep projected and unsettled proceeds excluded from purchasing power.
- Deduplicate capital uses and map verified held Radar names to `EXISTING_HOLDING_ADD`.

### Dual-phase orchestration

- Keep `POST_MARKET` as the sole completed-session technical and hard-risk authority.
- Create versioned pre-open policy, premarket snapshot contract, immutable post-market baseline, pre-open report/transition schemas, and a pre-open orchestrator.
- Pre-open may maintain or downgrade execution, surface overnight evidence, and re-evaluate fresh verified cash; it may not confirm daily technicals, create hard-risk breaches, quantity, or orders.
- Add run-phase-aware transition and delivery identifiers.

### Automation lifecycle

- Add non-broker automation delivery runtime with `NOT_CONFIGURED`, `CONFIGURED`, `FIRST_RUN_PENDING`, `DELIVERY_VERIFIED`, and `FAILED`.
- Provide exact post-market and pre-open Codex automation prompts and document manual setup when native task creation is unavailable.
- Do not install Windows Task Scheduler or any OS daemon.

## Migration risks

1. Existing v2.2/v2.3 schema fixtures will require a controlled version migration without weakening previous negative tests.
2. Hard-risk provenance may be incomplete for an otherwise approved numeric rule; incomplete provenance must fail closed rather than silently inherit execution authority.
3. Independent provider availability may remain externally blocked. Correct fail-closed behavior is mergeable, but live readiness must remain `DATA_PROVIDER_BLOCKED`.
4. Premarket quote providers may not supply bid/ask/volume consistently. Missing fields remain explicit and may block pre-open execution refresh.
5. Codex scheduling capability may not support two native tasks in this task context; no OS-scheduler workaround is permitted.
