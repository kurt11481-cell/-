# 운영·개발 사용자 개입 줄이기 — 아이디어 (2026-10-09)

## 0. 결론

- 사람 손이 많은 원인은 3가지다. ① 시스템이 스스로 만든 검토·리플레이가 결정 질문을 낳고, 그 답의 절반쯤이 "현행 유지"다. ② 키움 자료 수집이 사용자 PC(PowerShell)에서만 되는데 정해진 실행자가 없어 사용자가 매 거래일 직접 돌린다. ③ 개발 한 건이 Cowork·터미널·Claude Code·Judge 창 사이 "옮겨 나르기"로 쪼개져 있다.
- 아이디어 16개(R9는 10-1 확인으로 불필요) 중 효과가 큰 4개: **R4 기본 처분 사전 등록**(결정 수 감소) · **R1 아침 수집 Windows 작업**(매일 PowerShell 0) · **D1 한 줄 Builder→Judge 파이프라인**(K2 한 건의 사람 단계 9 → 2) · **D5 개입 예산**(다시 늘지 않게).
- 바꾸지 않는 것: 키움 주문 입력, 확인 코드 apply, K3 승인·재고정, 병합, 정책 변경은 계속 사람이 한다. 자동화는 "모으기·계산·표시·멈춤"에만 쓴다.
- FX-1009 동결(fx-6까지 새 예약 작업·규칙 후보 금지) 때문에 새 예약 작업이 필요한 것(R1·R2·R7)은 fx-6 뒤에 한다. 지금 할 수 있는 것은 문서 규칙(K0)과 화면(K1)뿐이다.

## 2. 원인 3가지

1. **결정 생산 > 결정 처리.** 리플레이·검토가 "미달"이어도 사람이 "현행 유지"를 답해야 닫힌다. 미달 = 현행 유지는 이미 사전 등록 기준에 정해져 있는데도 사람 단계를 한 번 더 거친다.
2. **실행자 없는 결정론 작업.** 30분봉·거래내역 수집은 판단이 없는 읽기 전용 작업인데, Windows에서만 돌아서 사람이 실행자다. 선례(SEC 수집기 = Windows 작업 스케줄러)가 이미 있다.
3. **창 사이 전달.** 개발 단계마다 사람이 프롬프트를 붙여 넣고 결과를 옮긴다. 결과는 파일에 있으므로 옮길 필요가 없다.

### 4-1. D1 파이프라인 동작 (검증한 CLI 기능만 사용)

1. 사용자: `.\dev-run.ps1 <작업id>` 한 줄. 작업id로 `docs/claude/<작업id>-builder-prompt.md`를 찾는다.
2. Builder: `claude -p "Read docs/claude/<작업id>-builder-prompt.md and follow it exactly." --worktree <작업id> --model <지시문 머리말 값> --effort <값> --permission-mode acceptEdits --max-turns <N>`. **지시문은 파이프로 넣지 않고 파일 경로만 영어 한 줄로 준다**(10-3: Windows PowerShell 5.1 파이프는 한국어를 `?`로 바꾼다). Claude가 Read 도구로 UTF-8 파일을 직접 읽는다. 기존 `.claude/settings.json`의 deny·ask가 그대로 걸리고, 묻는 것은 `--permission-prompts none`으로 **거절**된다(멈춰 기다리지 않음). 판단이 필요하면 `BLOCKED.md`를 쓰고 끝내라고 지시문에 적는다.
3. 스크립트(결정론): 대상 테스트 + 전체 테스트를 직접 돌려 `test-baseline-2026-10-09.md` 대비 새 실패 수, `git diff --name-only`가 지시문의 허용 파일 목록 안인지, 테스트 수가 줄지 않았는지 판정 → 결과 파일. Builder 자기 보고는 증거로 쓰지 않는다.
4. Judge: 새 프로세스 `claude -p "Read docs/claude/<작업id>-judge-prompt.md and follow it." --model opus --effort xhigh --tools "Read,Grep,Glob" --output-format json`(Bash·Edit·Write 없음 = 읽기 전용 강제). Judge는 파일을 쓸 수 없으므로 결과는 표준 출력으로 받고, 스크립트가 `cmd /c "claude ... > <작업id>-judge.json"`처럼 cmd 리디렉션으로 바이트 그대로 저장한다(10-3, collect_30m.ps1과 같은 방식). 스크립트가 이 JSON에서 PASS/FAIL을 읽는다.
5. FAIL이면 같은 worktree에서 최소 수정 1회만 자동 재시도 → 다시 FAIL이면 멈추고 사람.
6. 사용자: 한 줄 결과(PASS/FAIL·새 실패 수)를 보고 `.\dev-merge.ps1 <작업id>`. 이 스크립트는 Judge PASS 파일·새 실패 0·허용 경로를 다시 확인한 뒤에만 병합한다. **K3는 4번에서 멈추고** 지금처럼 사용자 결정 + 재고정 절차.
- Cowork는 기존 규칙대로 worktree 결과를 직접 읽는다("Builder 완료" 전달 불필요). 관제판은 Cowork가 갱신.
- 모델·노력은 스크립트 인자로 들어가 사용자가 세션을 바꿀 일이 없다.

### 10-3. PowerShell에서 한국어 지시문을 Claude Code에 넘기면 깨지나
- **사용자 환경 = Windows PowerShell 5.1**: 저장소 스크립트가 5.1 동작을 피해 고쳐져 있고(`run_sec_scheduled_shadow.ps1` 13·279줄), 일반 PowerShell 실행에서 cp949 디코딩 오류가 났다(관제판 s-wintest·s-wintest-cp949).
- **파이프로 넘기면 깨진다(문서 + 실측 확인)**: Windows PowerShell 5.1의 `$OutputEncoding` 기본값은 ASCIIEncoding이고 "외부 프로그램으로 파이프할 때 쓰는 인코딩"이다(Microsoft about_Preference_Variables 5.1). ASCII 밖 글자(한국어)는 `?`로 바뀐다. 또 `Get-Content`는 BOM 없는 파일을 시스템 코드 페이지(ANSI, 한국어 Windows는 cp949)로 읽는다(about_Character_Encoding 5.1) → UTF-8 지시문 파일은 읽는 단계에서부터 어긋난다.
- **출력 쪽도 주의**: PowerShell이 외부 프로그램 출력을 받아 `>`로 저장하면 콘솔 인코딩으로 다시 해석한다(일반적으로 알려진 동작, 5.1 공식 문구는 이번에 찾지 못함 — 확인 필요). 저장소는 이미 `cmd /c "... > 파일"`로 바이트 그대로 저장하는 방식을 쓴다(collect_30m.ps1 31줄).
- **결론 — 깨지지 않게 하는 방법**: 지시문을 파이프로 넣지 않는다. `claude -p "Read docs/claude/<id>-builder-prompt.md and follow it exactly."`처럼 **영어 한 줄 + 파일 경로**만 주면 Claude가 Read 도구로 UTF-8 파일을 직접 읽어 인코딩 문제가 생기지 않는다. 결과 저장은 `cmd /c` 리디렉션. 4-1절 2·4번을 이렇게 고쳤다.
- 꼭 파이프가 필요하면: 스크립트 첫머리에 `$OutputEncoding = [System.Text.UTF8Encoding]::new($false)`, 읽기는 `Get-Content -Raw -Encoding UTF8`. 이 경우 Claude Code가 표준 입력을 UTF-8로 읽는지는 문서에 없음(확인 필요) — 그래서 권장하지 않는다.
- **실측 확인(2026-10-09 18:40 KST, 사용자 PowerShell `C:\Users\금동한`)**: `'한글' | python -c "import sys; print(sys.stdin.buffer.read())"` → `b'??\r\n'`. 한국어 두 글자가 `?` 두 개(0x3F)로 바뀌어 전달됨 → 파이프 전달은 쓰지 않는다(위 결론 확정).
