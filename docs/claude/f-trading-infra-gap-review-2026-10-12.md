## 1. 결론

- **주문 2단계(키움 API 주문 + 휴대폰 승인 1번)는 지금 코드가 아니라 "빠진 부품"(제출 전 관문 · 주문 장부 · ACK_UNKNOWN 대조 · 승인 채널 · 호스트 점검)이 문제다.** 도구를 새로 들일 필요는 없다. 6개 항목 판정: 직접 구현 3 · 보류 3 · 도구 채택 0.
- **가장 큰 새 발견 3개**
  1. 키움 주문 API에는 **클라이언트 주문 ID(멱등 키)가 없다**(ust20000 요청 칸: 거래소·종목·수량·단가·매매구분뿐, 응답에만 `ord_no`). 같은 주문이 두 번 나가는 것을 서버가 막아주지 않는다 → 중복 방지는 **우리 쪽 장부 + 제출 전 미체결 조회**로만 가능하다.
  2. 코어 Windows 작업은 **"사용자 로그온 상태에서만 실행"**이고 절전에서 깨우지 않는다. PC가 24시간 켜져 있어도, Windows 업데이트 재부팅 뒤 로그인 화면에서 멈추면 코어도 멈춘다. 자동 로그인 여부는 **확인 필요**.
  3. **미체결이 "있는" 응답은 실계좌로 한 번도 못 봤다**(없음 응답만 실측). 2단계 대조 장치의 핵심 경로가 합성 테스트로만 검증돼 있다.
- **T5 질문 전에 끝내야 할 것** = 4절의 후보 C1~C6. 그중 사용자 손이 드는 것은 T5 질문 때의 결정 3개뿐이다(승인 채널 · 모의 계정 · 취소 권한).
- 1단계(주문표 사람 입력)에는 이 문서의 어떤 항목도 필요 없다. 1단계가 도는 동안 읽기 전용으로 증거를 모으는 것(C4)이 오히려 가장 값싼 선행 작업이다.

## 3. 2단계 실행 흐름 설계안 (T5 승인 뒤 구현, 지금은 설계만)

의도(T2 주문표) → ① 제출 전 관문 → ② 사용자 승인 → ③ 제출 → ④ 응답 처리 → ⑤ 체결 확인 → ⑥ 대조(기존 T1 코어).

1. **제출 전 관문(전부 통과해야 제출, 하나라도 실패면 제출 안 함 + 알림)**: 오늘 날짜의 `LATEST`·`LATEST_DECISION` 신선 · 단계 플래그가 2단계 · kill_switch=false · 주문표가 비교 모드 아님 · 같은 종목의 미체결 조회가 **VERIFIED_NONE**(또는 우리 장부가 설명하는 것) · 우리 장부에 같은 idempotency_key 없음 · 토큰 유효.
2. **장부 2단계 기록**: 제출 *전에* `SUBMITTING`(의도 해시, 종목·수량·가격·시각)을 쓰고, 응답을 받으면 `ord_no`로 갱신한다. PC가 제출 중에 죽어 `SUBMITTING`만 남으면 재시작 때 **ACK_UNKNOWN**으로 보고 재전송하지 않는다.
3. **ACK_UNKNOWN / 응답 없음**: 맹목 재시도 금지(`docs/future-order-readiness.md:14`). 미체결 조회(ust21050)와 당일 주문 조회(ust21150)에서 종목·수량·가격·시각이 맞는 주문을 찾아 `ord_no`를 붙이거나, 없음이 확인되면 `NOT_SENT`로 닫는다. 판단이 안 되면 알림 + 해당 종목 제출 잠금(fail-closed).
4. **체결 확인**: 다음 날 06:15 코어가 체결 내역으로만 분류(가격으로 추정 금지 — 현행 규칙 그대로). 같은 날 저녁 확인이 필요하면 미체결·당일 체결 조회를 한 번 더 읽는다(읽기 전용).
5. **취소·정정(ust20003·ust20002)**: 2단계에서는 **자동으로 하지 않는다.** 필요하면 승인 1번에 묶는다(6절 결정 3). 긴급 정지(kill_switch)는 "새 제출 차단"만 하고, 이미 나간 주문의 취소는 사람이 한다 — 취소 자동화는 3단계 조건.
6. **제출 모듈은 에이전트 도구 밖에 둔다**: Windows 작업이 실행하는 별도 스크립트. 데스크톱 앱 주문 게이트 0·브리지의 주문 엔드포인트 차단·Builder deny는 그대로 유지한다. 이 모듈이 키움 주문 API를 부르는 *유일한* 코드가 되고 권한 경로(`authority-paths.txt`)에 등록한다. OpenShell류 격리는 Windows에서 실험 지원이라 보류 — 대안(별도 Windows 계정·폴더 권한)은 **확인 필요**.
7. **키움 호출 직렬화 + 토큰 단일 소유**: 같은 앱키로 새 토큰을 받으면 기존 토큰이 서버에서 무효가 되는 현상이 재현됐다(8005, `kiwoom-token-reuse-review-2026-10-06.md` 1절, 토큰 수명 약 24시간). 주문 단계에서는 "제출 → 응답 → 조회" 사이에 토큰이 끊기면 ACK_UNKNOWN이 늘어난다 → 제출 모듈이 호출 파일 잠금(한 번에 한 프로세스)을 잡고, 토큰 재발급은 하지 않는다(현행 규칙).

## 6. T5 질문 때 사용자가 정할 것 (기본값 포함, 지금은 묻지 않는다)

1. **승인 채널**(휴대폰 승인 1번을 무엇으로): 후보 (가) Claude 앱에 "승인 <주문표 id>" 보내기 → 승인 파일 → 제출 모듈이 확인 · (나) 키움 앱 자체 승인 · (다) Paperclip류. 비교 시작점은 (가) — 새 서브시스템이 없고 주문표 id·만료 시각·종목·수량·가격을 승인 메시지에 못 박을 수 있다. 기본값으로 정한 것은 아니다. 확인 필요: (나)의 존재 여부, (가)의 만료·재사용 방지 설계.
2. **모의 계정**: 모의 도메인이 쓸 수 있으면 개설 1번 vs 모의 없이 최소 수량 실주문. 기본: 모의 가능하면 모의 먼저.
3. **취소·정정 권한**: 2단계에서 취소를 승인 1번에 묶을지 사람만 할지. 기본: 사람만(현행 "취소 금지"와 같음).

## 7. 확인 필요 (이 세션에서 못 확인한 것 — 만들어 쓰지 않았다)

- 코어 작업 PC 설정: 자동 로그인·전원 계획·Windows 업데이트 재부팅 시간(C1이 풀어 준다).
- 키움: 토큰 자동 만료·재로그인·정기 점검 시간, LOC 접수 마감 시각(재설계 문서 202행도 같은 항목), REST 호출 한도, 스트림 비용·동시 연결 수, 미국주식 모의투자 지원.
- F4(실시간 주문확인)가 HTS/MTS 수동 주문도 받는지(명세는 "토큰을 발급한 계좌에 주문이 발생하면 수신"이라고만 한다. `EXTERNAL_MANUAL_ORDER_DETECTED` 분류가 이것에 기대는지는 미확인).
- 미체결 "있음" 응답의 실제 모양(`open-orders-diagnosis-2026-09-30.md` §3-4와 같은 한계).
- SEC shadow 수집 작업의 현재 사용 여부.

## 8. 이번에 하지 않는 것 (군살 방지)
