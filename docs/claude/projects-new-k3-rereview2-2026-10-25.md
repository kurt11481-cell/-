# 결론
1. **개정본은 아직 K3 Builder 지시문의 근거로 쓰기 어렵다.** 1차 9항목 중 7개 반영, 2개 부분 반영. 가장 큰 구멍은 (나) 승인 검증 규칙에 막지 않은 공격 경로가 남은 것이고, 되돌림 줄이 "결정 아님 제안"으로만 있는데 8절은 이미 있는 규칙처럼 쓴다.
2. **인용 행 번호는 대부분 맞다.** CLAUDE.md·journal.py·reconcile 인용은 맞고, adoption 4곳과 sc-1022 1곳이 틀렸다.
3. **① 대상 파일이 빠졌다.** 승인 방식 값의 실제 정의는 `apply_user_confirmed_broker_snapshot.py:30`이고, 일지 스키마의 `confirmation_method` enum(29행)과 `additionalProperties:false`(6·17행) 때문에 메시지 id 칸을 넣으려면 스키마 변경이 필요하다.
4. 순서는 그대로: cashflow-api-gap(cf-b2n)이 먼저.

# (나) 공격 경로 점검
| 경로 | 개정본 | 판정 |

| 코디네이터가 코드·문장을 만들어 전달 | 작성자=사장, id 직접 읽음 | 부분 — 서버 작성자 필드 신뢰성은 시험 전까지 확인 필요 |
| send_later·트리거·예약 실행 | 거부 | 부분 — 트리거가 넣은 턴이 사장 계정으로 찍히면 통과. 사람 직접 입력인지 출처 확인 필요 |

| 전날 메시지 | 같은 KST 날짜 | 막음 |
| 다른 계정 | "작성자=사장"만 | 부분 — 표시 이름이 아니라 고정 계정 id로 비교 |
| 편집된 메시지 | 없음 | **미반영** |
| 같은 id를 일지·대조 원장에 한 번씩 사용 | 원장마다 1회용 | **미반영** — 두 원장 합쳐 1회용 |

- **구조적 한계(명시할 것):** 작성자·시각·날짜 확인은 LLM 스레드가 하고, apply 스크립트는 서버를 조회하지 못해 id 중복만 강제할 수 있다. 실행 경로도 deny를 우회하는 Desktop Commander라 "정해진 명령만"은 지침 문장 수준의 통제다. 병합 즉시 효력이므로 이 한계가 그대로 운영 위험이다.

- 일반 dev-merge(CLAUDE.md 54-55, 115)를 사장실 스레드로 옮기면 Q1 b(승인류) 범위를 넘는다. 담당 미정.

- 기존 결함: 지침 3절 "개발 큐 등록"은 CLAUDE.md 52-53("Cowork writes … and queues")과 어긋난다.
