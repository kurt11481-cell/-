# 대시보드 디자인 구성·운영 사례 검토 (2026-10-05)

읽기 전용 검토. 대시보드 HTML·저장소·예약 지시문·정책·상태 파일은 바꾸지 않았다. order_authority=false.
앞 검토: `external-dashboard-secondbrain-review-2026-10-05.md`(후보 A·C·D·E·F). 이 문서는 같은 절차로 웹 사례를 대조하고 후보를 이어 붙인다(G1~G6).

## 0. 결론
1. 두 대시보드의 뼈대(맨 위 결론 → 핵심 숫자 → 상세, 지금 할 일 1개 + 따라 하기, 데이터 소유자 1명, 주간 점검)는 사례 원칙과 맞다. 다시 만들 이유는 없다.
2. 사례 대비 진짜 빈칸은 하나다: **통합점검이 오래된 기록을 보여줘도 경고가 없다.** 예약 지시문은 대시보드 기록에 실패하면 "푸시하지 않는다"(v3.8 86행)라서, 기록 실패 날에는 알림도 화면 경고도 없이 지난 결과가 그대로 보인다 → G1.
3. 나머지는 작게 다듬기: G2 핵심 숫자에 직전 점검 대비 변화(이미 불러온 기록으로 계산), G3 결론 한 줄 길이 상한(10/3 결론 209자), G4 푸시에 대시보드 주소.
4. G1·G2는 화면만 바꾸는 일이라, 아직 재게시 전인 A(관제판 작업 c-check-fold)와 묶으면 재게시 1회로 끝난다. G3·G4는 지시문 문구라 다음 지시문 변경 때 묶는다.

## 1. 사례에서 뽑은 원칙 — 사실/해석/가설
- 사실(출처 원문에 있는 내용): Few의 대시보드 정의와 흔한 실수 13가지(2006), Shneiderman의 "개요 먼저, 확대·거르기, 필요할 때 상세"(1996), Grafana 성숙도 모델(버전 관리, 주기적 정리, "대부분의 대시보드는 알림에서 연결돼야"), Kanban 흐름 지표 4개(진행 중 개수·처리량·작업 나이·소요 시간), WCAG 1.4.1(색만으로 정보를 전달하지 않기), 데이터 신선도 기준과 경보.
- 해석: 사례들의 공통점은 "질문 하나에 답하는 화면", "무엇이 바뀌었나를 먼저", "오래된 데이터는 숨기지 말고 표시".
- 가설(검증 안 됨): 이 원칙을 적용하면 아침 파악 시간이 줄고 놓치는 일이 준다는 효과. 앞 검토의 E(효과 기준 기록)로 확인한다.

## 2. 두 대시보드와 대조 (읽기 전용 확인, 2026-10-05)
| 원칙(출처) | 개발 관제판 | 통합점검 | 판정 |

실측:
- 통합점검 저장 기록 2건(10/2, 10/3). 10/3: 결론 209자, 상태 칩 8개, 확인 필요 14개, 종목 9개, 일정 10개, 레이더 9개.
- 화면 코드: 점검 기록을 최근 30개까지 불러와 고르기 칸에 쓴다 → 직전 기록이 이미 화면 안에 있어 G2는 새 데이터 없이 계산만 하면 된다.
- 예약 일정: 통합점검 화~토 06:10 KST. 오늘(월)은 토요일 기록이 최신인 것이 정상.
- 통합점검 HTML 마지막 게시 10/3 → A는 아직 재게시 전.

조건부(지금은 안 함):
- G5 대시보드 HTML 사본을 저장소에 보관(재게시할 때마다). 아티팩트 서비스의 이전 버전으로 되돌릴 수 있는지 먼저 확인하고, 안 되면 도입.
- 앞 검토 B(결정 N일째 미결)는 그대로 조건부.

하지 않음:
- 차트·게이지 추가 — Few #5·#11(맞지 않는 표현 방식, 쓸모없는 장식). 지금 정보는 숫자·막대로 충분.
- 실시간 갱신 — 데이터가 하루 한 번 바뀐다.
- 색 체계 변경 — 한국식 등락 색 + 글자 표시로 WCAG 1.4.1 충족.
- 작업 나이·진행 중 개수 지표 — 관제판 상태는 세션 끝에만 바뀌어 숫자가 부정확. 주간 점검 R6로 대체.

### 3-1. 묶어서 하는 순서(제안)
1. **A 재게시(c-check-fold)에 G1·G2(+G6) 포함** — 통합점검 화면 1회 재게시.
2. 관제판 다음 재게시 때 D(+G6).
3. 다음 통합점검 지시문 변경 때 G3·G4.
4. 10/10 이후 C(1주 사용 뒤 정리) — 이때 "5초 테스트"(화면을 열고 5초 안에 오늘 판단할 것이 있는지 말할 수 있나)를 같이 본다.

### 3-2. 사용자 결정 (2026-10-05)
- G1·G2를 A와 묶어 통합점검 재게시 1회로 처리하기로 승인. 관제판 작업 c-check-fold 범위·시작 문구 갱신(Sonnet · high). G3·G4·G6·C·D·E는 위 순서대로 대기.

## 5. 왜 틀릴 수 있나
- G1의 "있어야 할 날짜" 계산이 미국 휴장·예약 시각 변경에 어긋날 수 있다 → 경고 문구를 "확인 필요" 수준으로 쓰고 판정에는 쓰지 않는다. 예약 시각이 바뀌면 화면 상수도 같이 고쳐야 한다(관제판 주간 점검 R1처럼 어긋남 위험).
- G2의 직전 값이 잠정 종가라 변화가 실제보다 크게 보일 수 있다 → "잠정" 표시를 그대로 붙인다.
- A에 G1·G2를 묶으면 한 번에 바뀌는 범위가 커진다 → 바뀌는 줄을 먼저 보고 승인하는 기존 절차 유지.

## 6. 확인 필요
- 예약 작업 푸시를 휴대폰에서 눌렀을 때 문구 속 주소가 눌리는 링크가 되는지(G4 효과 전제).
- 아티팩트 서비스에서 이전 화면 버전으로 되돌리기가 가능한지(G5 판단 전제).
- 미국주식 현황판과 통합점검 계좌 상세가 같은 정보를 겹쳐 보여주는지(이번 검토 범위 밖, 읽지 않음).
