# last30days에서 빌린 생각으로 기존 기능 고치기 — 아이디어 (2026-11-27 KST)

결론: 🟡 새 도구 없이 지금 기능 안에서 고칠 것 6개. 살펴보다 **이미 있는 구멍 2개**를 찾았다. 하나는 수집 종목 명단에 CRWD가 빠진 것이고, 다른 하나는 finviz 수집이 실패해도 알림이 없는 것이다. 이 둘을 먼저 고치고(0순위), 그다음 실적 날짜 바뀜 알림(1순위)을 넣는다. 모두 표시·점검 열기용이고 매매 규칙·노출·한도는 바꾸지 않는다. 착수는 묶음마다 사장 카드 1건.

근거 문서: last30days-review-2026-11-27.md(같은 폴더). 대상 기능 현행판: 외부 정보 수집 v0.6(info-monitoring README), 시나리오 확률 점검 v2.4, daily/2026-11-27.md, data/finviz.jsonl.

## 0-가. 수집 명단에 CRWD 넣기 (먼저)
- 사실(11/27 15:1x KST 확인): 회사PC card-evidence-registry.json에는 CRWD가 관심 종목으로 있는데, 수집 명단 tickers.txt(11/06 커밋 ee2379c 기준 10종목)에는 없다. 명단 대조는 매주 월요일인데, 회사PC에 연결이 안 되면 넘어가고 알림이 없다(README 38·47~52행). 11/09·16·23 대조가 왜 못 잡았는지는 확인 필요.
- 고칠 것: 명단 대조를 기존 절차대로 다시 하고, '월요일 대조 n주 연속 넘어감' 1줄 알림을 더한다.
- 연결표: 자료 등록부 symbols(연결) → 읽는 점검 월요일 명단 대조(끊김 — 넘어감이 조용함) → 바뀌는 행동 tickers.txt 고침(연결, 기존 절차) → 끊김 알림 넘어감 알림(끊김, 새로 만듦).
- 승인 경로: 명단 고침은 수집 주인 스레드의 기존 절차. 알림 줄이 지시문에 닿으면 `예약 작업 변경 승인: 외부 정보 수집`, 코드만이면 collect.py 판 올림 + 사장 카드.

## 0-나. finviz 연속 실패·누락 알림
- 사실: finviz 기록이 11/22·11/23에 없다(data/finviz.jsonl, daily 11/22 파일 없음·11/23 'finviz 없음'). 원인 확인 필요. collect.py의 finviz 명령은 일부 실패에 종료 코드 2만 내고 연속 실패를 세지 않는다(857~876행). 연속 실패 세기는 숫자 수집에만 있다(835~842행).
- 고칠 것: 숫자 수집과 같은 방식으로 finviz도 2회 연속 실패·누락이면 1줄 알림.
- 연결표: 자료 finviz(연결) → 읽는 점검 없음 → 바뀌는 행동 수집 고침(사람) → 끊김 알림(끊김, 이번에 메움).
- 승인 경로: collect.py 판 올림 + 사장 카드(v0.4·v0.6 선례, 지시문 그대로일 때).

## 1. 실적 날짜 바뀜·임박 알림
- 문제: 11/24 통합 점검이 CRWD 실적을 12/01로 두었지만 실제 발표는 11/23이었다(crwd-zs-acq-1124.md, SEC 8-K 0001535527-26-000035).
- 주의: finviz 'Earnings' 칸은 '다음 실적일'이 아니다. 다음 날짜가 정해지기 전에는 지난 실적일을 보여 주고 연도가 없다(finviz.jsonl: DELL 11/08까지 'Sep 01 AMC' → 11/09부터 'Nov 24 AMC', MU 11/21까지 'Sep 30 AMC' → 11/24부터 'Dec 17 AMC'). 그래서 '점검 기록과 다르면 알림'으로 만들면 거의 매일 울린다.
- 고칠 것(1단계): 수집기 안에서만 **값이 전날과 바뀐 날**과 **7일 안으로 다가온 날**에 daily 파일에 1줄을 쓴다. 지난 날짜는 '지난 실적일' 표시만 하고, 연도는 수집일로 추정한다.
- 2단계(따로): 통합 점검이 쓰는 실적 예상일 파일 earnings-anchors.json(결정 earn-na, active-decisions 239행)과 대조. 이 파일이 회사PC에 있으면 06:20 클라우드 실행에서 못 읽을 수 있다(확인 필요).
- 지키는 선: 수집기는 통합 점검 파일을 쓰지 않는다(README 5·81행). 날짜 고침은 통합 점검 주인이 EDGAR 8-K·IR로 확인한 뒤 기존 절차로 한다. finviz는 '바뀌었다'는 신호일 뿐이다.
- 연결표: 자료 finviz Earnings(연결, 이미 수집) · earnings-anchors.json(끊김, 읽는 길 확인 필요) → 읽는 점검 통합 점검 일정 확인(끊김) → 바뀌는 행동 점검 할 일 열기까지(끊김, 날짜 고침은 통합 점검 절차) → 끊김 알림 0-나와 함께(끊김).
- 승인 경로: 1단계 = collect.py 판 올림 + 사장 카드. 2단계가 통합 점검 규칙·지시문에 닿으면 `예약 작업 변경 승인: 보유·관심 종목 통합 점검` + 독립 검토.
- 선행 조건: 0-가(CRWD가 명단에 없으면 CRWD는 못 잡음).

## 2. 한 달 성과 대 QQQ 표시
- 사실: finviz 'Perf Month'는 이미 받는데(collect.py 70행) daily 표에는 Perf Week만 나온다(1230행). ETF(SOXL·MVLL)도 값이 있다.
- 고칠 것: 표에 'Perf Month(finviz 정의)' 칸과 QQQ 한 행을 더한다. QQQ는 tickers.txt가 아니라 collect.py의 기준 지수로 따로 받는다(명단에 넣으면 월요일 대조가 지움).
- 지키는 선: 가격 판정은 키움. 종목 고르기 실력 점수(pick-vs-qqq, 26주 고정)와 별개의 참고 표시이고 그 점수에 넣지 않는다.
- 연결표: 자료(연결, 이미 수집) → 읽는 점검 보유·관심 카드 점검 참고(연결 — README 기재, 실제로 읽히는지는 확인 필요) → 바뀌는 행동 의도적 없음 — 사장 결정 필요 → 끊김 알림 0-나에 포함(끊김).
- 승인 경로: collect.py 판 올림 + 사장 카드. 0-나와 한 판으로 묶을 수 있다.

## 3. 안 쓰는 finviz 칸 정리 (SIMPLIFY)
- 사실: finviz에서 받는 칸 가운데 약 11개가 daily 표에 쓰이지 않는다(collect.py 67~71행 대 1230행). README 8행 "소비자 없는 자료는 모으지 않는다"와 어긋난다.
- 고칠 것: 소비자가 있는 칸만 남기거나, 남길 칸의 소비자를 적는다. 2번과 함께 한다.
- 승인 경로: 2번과 같은 판.

## 4. X 글 참여도 적기
- 고칠 것: X 글마다 조회·좋아요·재게시 수를 적고, 세 계정이 같은 날 같은 이야기를 하면 '겹침 2계정'으로 묶어 표시한다.
- 걸림: X 화면에는 data-testid가 없고, 도구 출력이 약 1,000자에서 잘린다(bin/x-read.js 2~3행). 수를 안정적으로 읽는 방법부터 시험해야 한다. 지금 쓸모 점검(usage)은 분류·소비자 칸만 센다(collect.py 931~946행).
- 순서: 12/05 쓸모 점검은 지금 방식대로 한 번 돌고, 참여도 첫 집계는 그다음 4주 집계부터다. 12/05 결과에서 계정이 '쓸모 0'이면 이 아이디어는 접는다.
- 지키는 선: 참여도는 판정에 안 씀. 커뮤니티 = 가설 등급. 좋아요·팔로우 같은 조작은 계속 금지.
- 연결표: 자료 참여도(끊김, 새로 읽기) → 읽는 점검 4주 쓸모 점검(끊김, usage 고쳐야 함) → 바뀌는 행동 계정 내리기·더하기 후보(끊김, 사장 카드) → 끊김 알림 수를 못 읽으면 빈칸 + X 실패 알림(끊김).
- 승인 경로: 지시문·x-read.js가 바뀌므로 `예약 작업 변경 승인: 외부 정보 수집` + 독립 검토.

## 5. 채용·특허 가설 줄 (손으로 시범)
- 고칠 것: 관심 카드 재검토 때 그 회사 공식 채용 페이지·USPTO 공개 검색을 한 번 보고, 새 분야가 보이면 외부 주장 원장에 가설 한 줄. 특허는 출원 약 18개월 뒤 공개라 선행 신호로 기대하지 않는다. robots 허용일 때만.
- 연결표: 자료(끊김) → 읽는 점검 원장 기록(연결, 원장 절차 = 사람 수락) → 바뀌는 행동 의도적 없음 — 사장 결정 필요(가설은 매매 근거 아님) → 끊김 알림 의도적 없음 — 사장 결정 필요(손으로 하는 일).
- 승인 경로: 시범 몇 번은 스레드에서 손으로 하고 원장 기록은 원장 절차. 카드 재검토 절차에 넣으려면 그 절차 변경 카드.

## 보류: 이야기 밑 확률 줄
- 처음 생각: X '시나리오 증거' 글 아래 그 시나리오의 시장 확률을 붙인다(last30days의 Polymarket 확률 줄).
- 접는 이유: 시나리오 점검이 이미 daily 파일을 읽는다(scenario-odds README 24·67·112행). 그 글을 읽는 쪽이 이미 확률을 가진 점검 자신이다. 그 점검의 변화 기준은 '기준값 대비'이고 7일 변화 값은 없다(같은 README 31·35·36행). 수집 쪽이 시나리오 파일을 거꾸로 읽는 새 의존도 생긴다.
