## 2. M2 동작
- **한국 날짜:** UTC + 9시간으로 직접 계산한다(Windows 시간대 설정과 무관).
- **계산기 고정:** 계산기 파일의 sha256(LF 정규화)이 실행기에 고정한 값과 다르면 계산기를 돌리지 않는다. 그때는 `verdict ERROR · ORACLE_SHA_MISMATCH`를 쓴다. 계산기를 고치려면 새 sha + Judge 확인이 필요하다(사전 등록 C1 "계산기 수정(새 sha, Judge 확인)").
- **실행:** `python -I docs/claude/t2rc-oracle.py check --day <날짜>`
- **결과 파일:**
  - 그날 decide 폴더가 있으면 `workspace/outputs/auto-core/<날짜>/t2rc-check.json`에 쓴다. 폴더가 없으면 logs 폴더에 쓰고, decide 폴더는 만들지 않는다.
  - 늘 `LATEST_T2RC_CHECK.json`에 복사한다.
  - 실행 전에 그날 결과 파일을 지운다. 그래서 같은 날 다시 돌다 계산기가 죽으면 앞선 결과가 남지 않는다.
  - 계산기를 못 돌린 경우(파일 없음·sha 다름·python 없음·출력 없음·날짜 형식 오류)에도 ERROR 결과를 쓴다. 그래서 08:50 알림이 옛 파일을 오늘 것으로 읽지 않는다.
- **판정 제외:** decide 결과가 08:40 뒤에 쓰였거나 아직 없으면 NOT_CHECKED다. 계산기가 decision.json이 쓰인 시각으로 판정한다. 작업이 늦게 돌아도(PC 잠자기 → 깨어난 뒤 실행) 기준은 같다.
- **쓰기 범위:** 결과 JSON 2곳 + 로그 1개뿐이다. 키움·주문·정책·상태·일지는 건드리지 않는다.
- **시험(클라우드, PowerShell 7.4 + cmd 대체 셸):**
  - 두 스크립트 모두 구문 오류 0, ASCII만 씀
  - sha 다름 → ERROR 파일 + 종료 3
  - python 없음 → ERROR + 3
  - decision 없음 → NOT_CHECKED + 0
  - 날짜 폴더 있음 → 그 폴더에 씀
  - CRLF 사본 → 같은 sha로 통과
  - 등록 -PlanOnly 출력 확인
- **확인 필요:** Windows PowerShell 5.1 실제 실행은 아직 안 했다. 적용 승인 세션에서 `-PlanOnly` → 등록 → 작업 1회 수동 실행(`Start-ScheduledTask`)으로 확인한다.

## 3. M3 바뀐 곳 (v2.1 대비 전부)
1. 머리 줄·목적 줄에 v2.2와 08:40 작업 이름을 넣었다.
2. 2) 받기 목록에 `R\LATEST_T2RC_CHECK.json` 1개를 더했다.
3. read.py 인자에 넷째 자리(독립 대조 파일)를 넣었다.
   - `R FRESH|STALE|NO_FILE` 줄을 출력한다.
   - 기록 모드(apply)에서는 주문표마다 허락 여부를 본다. 허락 = 그 방향이 전에 확인됨, 또는 그 주문표 id가 오늘 계산기의 일치 목록(c3.matched)에 있음. 계산기가 못 본 주문표(08:40 뒤 재실행 등)는 허락되지 않는다. 오늘 파일이 아니거나 없으면 허락 안 함(fail closed). 허락되지 않은 주문표는 다음과 같이 한다.
     - 그 종목이 든 PUSH 줄을 뺀다.
     - `D HOLD <방향> <종목>` 줄을 낸다.
     - 입력 안내(NEXT_USER)는 허락된 건수로 다시 쓴다("주문표 m건 — 저녁 키움 입력 (확인 대기 k건은 입력 금지)"). 허락된 것이 없으면 비운다.
4. core.py 인자에 셋째 자리를 넣었다. 기록 모드의 orders 문서는 허락된 주문표만 쓴다. 대시보드 core에는 막힌 주문표에 "주문표 확인 대기 — 입력 금지" 표시를 붙인다(meta.ticketHold, tickets[].hold).
5. 알림 ⑫: 독립 대조가 MISMATCH·ERROR이면 1줄 보낸다. 결과가 없거나 오늘 것이 아닌데 decide 결과는 있으면 "독립 대조 결과 없음 — 확인 필요"를 보낸다.
6. 알림 ⑬: `D HOLD` → "주문표 확인 대기(<방향>: <종목>) — 입력 금지".
7. 금지 목록에 "독립 대조 결과 파일 수정·재실행"을, 출력 줄에 독립 대조 VERDICT를 더했다.
- **비교 모드(지금):** ⑬은 생기지 않는다(apply일 때만). ⑫만 동작한다. D0 전에도 불일치가 알림으로 보이는 것은 사전 등록 M2와 같은 동작이다.
- **시험(이 PC 리눅스 VM python, 실제 10-14 파일 + 가짜 기록 모드 3가지):**
  - 실제 10-14: v2.1과 같은 줄 + `R FRESH VERDICT MATCH`
  - 독립 대조 파일 없음 → `R NO_FILE`
  - 매도만 막힘 → SOXL 줄 빠짐, `D HOLD 매도 SOXL`, orders 1건(MU만)
  - 둘 다 막힘·파일 없음 → PUSH 주문표 줄 0, NEXT_USER 비움, orders 0

## 4. c3 기록 (계산기 출력, M3가 읽는 값)
- **방향별 값:** `{tickets_today, today_all_match, confirmed_before, entry_allowed}`
- **confirmed_before:** 앞선 날짜의 결과 중 그 방향 주문표가 그날 모두 일치한 날이다. 다음 조건을 모두 갖춘 결과만 센다.
  - 기록 모드(apply)다. 비교 모드 일치는 세지 않는다. 사전 등록 C3가 "T2를 켠 뒤 첫 주문표"라고 적었기 때문이다.
  - 판정이 MATCH·MISMATCH다. NOT_CHECKED·ERROR·자기 확인(INFO_*)은 세지 않는다(사전 등록 1절 "NOT_CHECKED 세션의 주문표는 C2·C3 확인으로 쓰지 않는다").
  - 지금과 같은 계산기 sha로 나온 결과다. 계산기를 고치면 확인을 다시 받는다.
- **entry_allowed = 오늘 그 방향 주문표 없음 · 전에 확인됨 · 오늘 그 방향 주문표 모두 일치** 중 하나라도 참이면 허락이다.
- **NOT_CHECKED인 날:** 이미 확인된 방향은 허락을 유지하고, 오늘 주문표는 불일치로 센다.

## 8. 독립 Judge 1차(2026-10-15, FAIL) 반영
- 알림 v2.2: 새 세션 없음 날 앞 기록에서 넘어온 주문표(dashboard.orders)도 허락 검사·HOLD·NEXT_USER 건수·core 표시 대상에 넣었다(read 52~54행, core 95~100행). 독립 대조 결과는 같은 decision(generated_at)을 본 것만 쓴다(read 48행, core 90행). 시험: 넘어온 주문표 미확인 → HOLD·입력 안내 없음·orders 0, 확인됨 → 입력 안내·orders 1, 다른 decision → HOLD. 평일 경로(매수 확인·매도 대기, 파일 없음)는 그대로.
- 남은 것: 아직 확인되지 않은 방향의 주문표는 발행일에 일치였어도 새 세션 없음 날에는 막힌다(오늘 대조의 matched가 비어서). 입력 기회를 잃는 쪽(안전 쪽)이다.
- 실행기: 계산기 새 sha로 고정값만 바꿨다. 클라우드 PowerShell 7 시험(정상·CRLF 사본)은 이번 고정값으로 다시 돌린다.
