## 2. 1단계 — 지침 7절 v2.4 문안 (사장이 프로젝트 설정에 넣음)

바꾸는 곳은 여섯 군데다. 나머지 행(Sonnet 세 행, Opus · high 행, 권한·K3용 Opus · xhigh 행)은 그대로 둔다. 제안서 12절의 "노력은 high까지"는 줄여 쓴 말이고, 권한·안전 검토의 xhigh는 유지한다.

1. 머리줄: `(v2.3, …)` → `(v2.4, … , 2026-11-18 "opus로 새 스레드의 작업 결과를 더 높이고 싶어서" · 다른 사용자 사례 적용)`
2. 첫 문장: `프로젝트 기본 모델은 Sonnet 5.5.` → `프로젝트 기본 모델은 Opus 5.5(결과 품질 우선).`
3. 둘째 문장: `코디네이터는 스레드를 열 때 아래 표에 맞춰 모델과 추론 노력을 처음부터 지정한다(스레드 안에서 갈아타게 하지 않는다).` → `코디네이터는 스레드를 열 때 아래 표의 모델과 추론 노력을 알린다. 회사PC 폴더 스레드는 지정이 먹지 않고 기본 모델로 시작하므로, 표와 다른 모델이 필요하면 스레드가 일을 시작하기 전에 한 줄로 알리고 사장이 첫 입력으로 맞춘다. 일을 시작한 뒤에는 모델을 바꾸지 않고 새 스레드를 연다.`
4. 표에 한 줄 추가: `- 예약이 깨우는 스레드: 옮겨 알리기 = Sonnet 5.5 · low, 정해진 순서 수집 = Sonnet 5.5 · medium, 판단이 들어가는 점검 = Opus · high`
5. Fable 행: `- 여러 스레드나 여러 달에 걸치는 큰 일의 기획·설계와 마무리 검수, 가장 어려운 종합 추론(여러 자료를 엮는 보유·매매 기준 검토, 전략 재설계, 마스터플랜, Opus 결과를 독립 재검토할 때, 사장이 Fable 지정): Fable 5.2 · high(그 위 노력은 쓰지 않는다). 사용 크레딧으로 청구되는 것이 확인되면 코디네이터는 Fable로 열지 않고 Opus · high로 대신한다(사장이 직접 지정한 경우는 그대로).`
6. 끝 문단: `"Opus 전환 권장" 또는 "Fable 전환 권장"` → `"Opus 새 스레드 권장" 또는 "Fable 새 스레드 권장"`

- 3번이 이 개정의 핵심이다. 지금 문구("처음부터 지정", "갈아타게 하지 않는다")는 폴더 스레드에서 지켜질 수 없었다(오늘 이 스레드: 지시 Sonnet 5.5 · high, 시작 Opus 5.5). '시작 전 맞추기'와 '도중 갈아타기'를 나눠 적는 것이고, CLAUDE.md "Never suggest switching model mid-session"(125~126행)과의 문구 맞춤은 정리 안건으로 올린다. 이 구분을 받아들일지는 사장 결정이다.
- '일반적인 전략 수립·로드맵'은 Opus · high 행 그대로다. 어느 쪽인지 애매하면 지금 규칙대로 한 단계 낮게(Opus) 시작한다.
- 개발 큐 지시문 작성은 표대로 Sonnet 5.5 · high다. 큰 일의 설계 문서만 Fable로 쓴다(3절).
- 되돌리기: v2.3 문구로 되돌린다. v2.3의 2절 예외·7절 사본은 프로젝트 파일 `token-usage-1118/review/instr-2-7.txt`에 있다.
- 주의: 기본 모델이 Opus인 동안 단순 확인·조회 스레드도 Opus로 돈다. 7일 한도가 걸리기 시작하면 2번을 다시 본다.
- CLAUDE.md 정리 안건으로 함께 올릴 것(급하지 않음, Opus · xhigh 절차): Session hygiene 문구와 7절 맞춤, 노력 변경 문장에 Fable 5.2 언급 여부, `/advisor` 한 줄(4절 규칙).

## 3. 2단계 — 큰 일은 세 걸음으로

대상은 '큰 일'만이다: 전략 재설계, 새 예약·새 시범처럼 지시문과 연결표가 필요한 일, 여러 스레드에 걸치는 일. 작은 질문·조회·한 파일 수정은 지금처럼 한 스레드에서 끝낸다.

| 걸음 | 모델·노력 | 하는 일 | 산출 |
|---|---|---|---|
| ① 설계 | Fable 5.2 · high | 목표·범위·하지 않을 것·검증 기준·연결표를 먼저 정한다 | docs/claude 설계 문서(개발 큐 지시문은 이 설계에서 표대로 Sonnet 5.5 · high가 쓴다) |
| ② 구현 | Opus 5.5 · high (개발 큐는 지금처럼 Builder opus) | 설계대로 만든다. 설계와 어긋나면 멈추고 알린다 | 코드·문서·보고 |
| ③ 검수 | Fable 5.2 · high, **새 스레드** | 설계와 결과를 원문으로 대조한다. 만든 스레드가 스스로 검수하지 않는다 | 검수 기록(맞음/틀림/빠짐) |

- 기존 절차와의 관계: 개발 큐의 Judge(Opus), CLAUDE.md V5 내장 재검토(따로 연 작업자)는 **그대로 한다.** ③은 그 위에 얹는 마무리 검수이고 대신하지 않는다. 권한·K3·CLAUDE.md/헌법 개정은 표대로 Opus · xhigh다.
- 스레드 수: 세 걸음은 차례로 연다(동시에 열지 않는다). 지침의 '동시 3개 이하'를 넘기지 않는다. Fable 스레드는 2절 3번대로 시작 전에 맞춘다.
- 시험: 다음 큰 일 2건에 적용하고 건마다 세 가지를 적는다 — 걸음별 사용량(get_session 환산), 검수에서 새로 나온 지적 수, 사장이 다시 손본 횟수. 2건 뒤 계속할지 정한다.
- 첫 대상 후보: llm-news 병합 뒤 '시범 켜기 + 결과 모음 연결' 제안, 5단계 마스터플랜에서 나오는 첫 과제.

## 4. 3단계 — `/advisor` 운영 (회사PC Claude Code 한정)

- 지금 상태: `/advisor fable` 저장됨(11:19 KST). 사용자 설정이라 그 PC의 Claude Code에 두루 적용된다. 공식 문서는 하위 작업자가 조언 모델을 물려받는다고 적고, `/advisor` 명령이 `-p`(자동 실행)에서도 동작한다고 적는다. 개발 큐의 Builder·Judge·test-runner와 Cowork 예약 작업에 실제로 붙는지는 확인 필요다.
- **먼저 할 확인(다음 개발 큐 실행보다 앞에):** 공식 문서는 Fable이 사용 크레딧 대상인 요금제에서 `-p` 실행은 "묻지 않고 청구한다"고 적는다. 제안서 11-3 A2는 이 확인 전에는 Fable 조언을 쓰지 않는 쪽이었다. 그래서 사장이 `/usage`에서 사용 크레딧 쪽 숫자를 먼저 본다. 오늘 11:34 KST에 llm-news가 이미 큐에 올라갔으므로, 이 실행 앞뒤 숫자를 비교한다.
  - 늘지 않음 → Fable 조언 그대로.
  - 늘었음 → `/advisor opus`로 낮춘다. 추가 사용량은 사지 않는다.
- 규칙(사람이 지키는 것, 이 계획의 판단):
  1. 조언은 V5 내장 재검토·Judge·K3 검토를 대신하지 않는다(제안서 11-3 A3).
  2. 조언 내용은 근거가 아니다. 결과물의 근거는 지금처럼 원문이다.
  3. API 시범(Agent SDK·API)은 조언 도구를 쓰지 않는다(api-pilots 72행 그대로).
- 이어서 볼 것(~11/25): 개발 큐 실행 1건과 Cowork 예약 1건의 세션 기록에서 조언 호출이 붙었는지. 붙어서 사용량이 크게 늘면 그 실행에서만 빼는 방법을 따로 제안한다(환경 변수 `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1`은 개발 파이프라인·예약 설정 변경이라 승인 경로가 필요하다).
- 프로젝트 스레드는 `/advisor`가 안 되므로 같은 효과는 2단계의 ③ 걸음(Fable 새 스레드 검수)으로 얻는다.

## 5. 4단계 — 영어 프롬프트 1건 시험

- 대상: **새로 쓰는 개발 큐 지시문 1건.** 기존 예약 지시문·CLAUDE.md·사장에게 가는 글은 바꾸지 않는다(사장 응답은 한국어, 예약 지시문은 변경 승인 대상).
- 방법: 언어만 바꾼다. 지시문은 평소대로 표의 모델(Sonnet 5.5 · high)이 쓰되 영어로 쓴다. 보고서는 지금처럼 한국어로 받는다고 지시문에 적는다. 저장소 규칙(코드 파일 ASCII, 한글은 `\U` 이스케이프)은 그대로다.
- 비교: 최근 한국어 지시문 실행들과 Judge 첫 판정(통과/재작업), 재시도 횟수, Builder 사용량을 나란히 적는다. 1건으로는 결론을 내지 않고 '계속 시험할지'만 정한다. 한계: 비교 대상인 지난 실행들은 조언 설정 전이라 조건이 완전히 같지 않다.
- 하지 않는 것: 기존 지시문 일괄 번역.

## 6. 5단계 — 마스터플랜

- 여는 법: 사장이 프로젝트 채팅에 한 줄 — `투자_V2 마스터플랜을 Fable 스레드로 짜줘`. 코디네이터가 회사PC 폴더 스레드를 열면 그 스레드는 일을 시작하지 않고 한 줄로 알리고, 사장이 첫 입력으로 `모델을 Fable 5.2로, 추론 노력을 high로 바꿔줘`를 넣은 뒤 시작한다(2절 3번 — 지금 지침 문구로는 예외이므로 1단계를 먼저 하는 것이 순서다).
- 지시문 뼈대(사례 문장을 이 프로젝트에 맞춤): "하루 이틀이 아니라 몇 달에서 몇 년이 걸릴 일이다. 목표는 사장이 대시보드 주문 지시만 보고 계좌를 운영하는 것. 지금 상태(관제판, active-decisions.md, 헌법 1.5.0, 진행 중 시범·예측 모형·시나리오 점검)를 원문으로 읽고, 단계·관문·중단 조건·측정 지표가 있는 마스터플랜을 짜라. 주문 권한은 넓히지 않는다. 확인 못 한 것은 확인 필요로 남겨라."
- 산출: docs/claude 마스터플랜 문서 1개 + 관제판에 단계별 작업. 계좌 금액·수량은 쓰지 않는다.
- 검수: 2단계 ③대로 다른 Fable 스레드가 한 번 본다. 권한·한도에 닿는 항목은 Opus · xhigh 검토와 사장 승인 경로로 따로 뺀다.
- 갱신: 분기 1회 또는 큰 결정(전략 재설계·권한 단계 변경) 뒤.
