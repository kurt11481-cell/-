# 주문 2단계로 가는 길 — 모의 주문 시험(K3) 안건 (2026-11-17)

계좌 금액·수량은 적지 않는다(비율·E만). 시각은 KST.

## 0. 결론

- **결정(2026-11-17 14:48:59 KST 사장 결정 카드 '모의 빼고 순서 그대로', 13절): 모의 주문 시험은 하지 않는다. 순서는 원래대로 둔다.** 3~8절은 닫힌 안의 기록이고, 지금 유효한 길은 14절의 길 1이다.
- 지금 유효한 순서(한 번에 하나):
  1. 읽기 관측. 사장이 키움에 직접 주문을 넣은 날 "미체결 읽어 줘"라고 치면 한다(14-2절 A). 권한은 바뀌지 않는다.
  2. '켜'. 2026-11-17 판정은 **미충족**이고 가장 빠른 충족은 11/18 아침(조건부)이다(t2-on-check-2026-11-17.md 결론·1절). 켜는 것은 사장이 대화창에 직접 치는 "켜"다.
  3. 1단계 실적(주문표 오류 0으로 10거래일 또는 주문표 5건 — automation-redesign-2026-10-10.md 132행). 그 사이 C2(호출 직렬화)는 권한 자리 순번대로 따로 승인받는다(14-3절).
  4. T5 질문(2단계를 열지). '예'면 제출 모듈을 만들고 '보내지 않고 돌리기' 다음 '최소 수량 실주문'으로 시험한다. 이 순서는 초안이고 T5 때 사장이 정한다.
- 하지 않는 것: 모의투자 신청·모의 앱키 발급(이 안건으로는 하지 않는다. T5 때 정할 '모의 계정' 항목은 그대로 남는다) · 키움에 토큰 영향을 더 묻는 일 · 착수 문구 `모의 주문 시험 착수 승인`.
- 이 결정으로 권한·규칙·코드·예약·순번은 바뀌지 않았다. 문서만 고쳤다.
- 2단계까지의 가장 긴 줄은 '켠 뒤 주문표 실적'이고 이 결정으로 줄지 않는다(automation-redesign-2026-10-10.md 132행).
- **이 안건이 풀지 못하는 것.** 11/05에 정한 3배 줄이기(ceo-open-actions.json A1, 아직 open)는 이 안건으로 실행되지 않는다. 2단계가 열려도 승인 1번은 사장 손이고, 여는 데는 여러 주가 걸린다. 그 주문은 사장이 키움에 직접 넣는 것이 가장 빠르다.
- **말의 뜻.** 이 문서에서 '직접 입력'은 사장이 대화창에 승인 문구를 직접 치는 것이다. 키움에 주문을 넣는 일은 '직접 주문'이라고 적는다.
- **무응답이면 아무것도 바뀌지 않는다**(9절).

## 1. 왜 이 안건인가

- 사장 지시(2026-11-17 11:29 KST 직접 입력): "시스템이 회사 자금 운영에 단순 조언 및 검토 수준을 넘어 적극적이고 지속적, 실시간으로 모니터링 및 개입해야 한다."
- 사실: 11/05에 정한 '3배를 계좌 10%까지 한 번에'가 11/09 '적기'·11/16 '기한' 알림 뒤에도 실행되지 않았다(ceo-open-actions.json A1 `status: open`, `alerts_md`).
- 시스템이 '개입'(주문 제출)하려면 주문 단계가 올라가야 하고, 올리는 것은 사장만 할 수 있다. "시스템은 자신의 Authority Envelope를 스스로 확대할 수 없다"(constitution-v1.5.0.md 530행). 지금은 `order_authority = false`(같은 문서 995~1005행).
- 10/31 검토가 2단계로 가는 첫 걸음으로 '모의 주문 리허설 앞당기기'를 냈지만 그날 사장 카드는 다른 안을 골랐다(system-evolution-2026-10-31.md 133~156행 · 235~238행 "고르지 않은 것: 모의 주문 리허설(K3) … 현행 유지"). 11/17 카드가 이 안건 문서까지를 다시 열었다.

## 3. 안건 — 모의 주문 시험

> **닫힘(2026-11-17 14:48:59 KST 사장 결정, 13절).** 이 절은 하지 않기로 한 모의 주문 시험 안의 기록이다. 지금 유효한 길은 14절 길 1이다.

### 3-1. 무엇인가
- C3 제출 모듈을 **모의 주소 전용**으로 먼저 만들어 배관을 시험한다. 돈은 0이다(system-evolution-2026-10-31.md 134행).
- 목적은 증거 건수가 아니라 배관 확인이다: 제출 모듈 · 제출 전 장부 · 응답 불명(ACK_UNKNOWN) 처리 · 토큰 단일 소유 · 승인 파일. 그리고 2단계 선행 조건 '모의 N거래일 오류 0'을 미리 채운다(같은 문서 135행 · f-trading-infra-gap-review 66행).
- 이 시험은 **단계를 올리지 않는다.** 실계좌 주문(2단계)은 별개의 T5 결정이다(system-evolution 146·156행).

### 3-2. 순서

```
[M0 확인 2건]  권한 자리 안 씀
   ├─ 하나라도 안 됨 → 멈춤(NO_CHANGE)
   └─ 둘 다 됨
        ↓
['켜' + 권한 자리 차례]
        ↓
[M1 착수]  사장 직접 입력
        ↓
[M2 만들기 ①]  C2 + 모의 프로필 예외 → 병합
        ↓
[모의 앱키 → 모의 조회 1건]  ㉮ 실측
        ↓
[M2 만들기 ②]  모의 제출 모듈 → 병합
        ↓
[M3 리허설 N거래일]
        ↓
[M4 결과 보고]  T5는 별개
```

- **M0 확인 2건(코드 없음).**
  - ㉮ 키움 모의투자가 미국주식 주문·미체결·당일 주문 조회를 실제로 받는가. 명세는 주소만 적고 TR별 지원 여부를 말하지 않는다(c6-mock-domain-check 11행 · 근거 절).
  - ㉯ 모의투자 신청·모의 앱키 발급·모의 토큰 발급이 실계좌 토큰을 무효로 만들지 않는가. 같은 앱키로 새 토큰을 받으면 기존 토큰이 무효가 되는 현상은 이미 재현됐다(f-trading-infra-gap-review 45행). 모의 앱키가 별개인지는 확인 필요다.
  - 방법: 키움 고객센터·Open API 문의. 사장 계정이 필요한 사람 단계 1번이다. 문의 글 초안은 부록에 있다. 공개 자료(명세·웹)로는 확인되지 않았다.
  - **㉯가 풀리기 전에는 모의투자 신청·모의 앱키 발급을 하지 않는다**(위원회 반영, 7절). 실계좌 토큰이 끊기면 매일 도는 코어 조회가 멈출 수 있다.
  - 갈림: ㉮가 '안 됨'이면 이 안건은 멈춘다. '모의 없이 최소 수량 실주문'은 T5 때 사장이 정할 항목이고 이 안건에 넣지 않는다(f-trading-infra-gap-review 72행). ㉯가 '영향 있음'이면 모의 앱키를 발급하지 않고 멈춘다(NO_CHANGE). 다시 볼지는 사장이 정한다.
- **M1 착수.** 사장 직접 입력(8절 문구) → 수동 경로 Builder → 독립 Opus Judge → 사장 PowerShell 병합(CLAUDE.md 66~82행 · system-evolution 151행).
- **M2 만들기 순서.** 병합은 2번 이상이 될 수 있다(정확한 묶음은 착수 때 지시문에서 정한다).
  - ① C2(호출 직렬화·토큰 단일 소유. 원문은 권한 경로라 '승인 1번 + 병합'으로 적는다 — f-trading-infra-gap-review 54행)와 모의 프로필 예외(CLAUDE.md 55행)를 먼저 병합한다. 이 안건의 착수 승인 1번이 C2 작업 시작까지 덮는 것으로 쓴다(권한 자리 1칸, 8절 4번). 병합은 묶음마다 사장 PowerShell로 따로 승인한다.
  - 그 뒤 사장이 모의투자 신청·모의 앱키를 넣고(㉯가 풀린 뒤에만), 모의 조회 1건으로 ㉮를 실측한다(system-evolution 142·156행).
  - ② 모의 전용 제출 모듈(제출 전 장부 SUBMITTING · ACK_UNKNOWN 대조 · '승인 <주문표 id>' 직접 입력으로 만드는 승인 파일 (가)안. f-trading-infra-gap-review 39~45·71행)을 병합한다.
- **M3 리허설.** 모의 계좌에 합성 소량 LOC 주문을 N거래일 넣는다. 종목·수량·N은 착수 때 Builder 지시문에서 사장이 확인한다(이 문서는 숫자를 정하지 않는다. 참고: 1→2단계 조건의 길이가 10거래일이다).
- **M4 결과 보고.** 합격이면 선행 조건 한 줄이 채워질 뿐이다.

### 3-3. 합격 기준(초안 — 착수 전에 고정)
중복 제출 0 · 응답 불명 미해결 0 · 우리 장부와 모의 미체결·당일 주문 조회의 불일치 0 · 실계좌 주소·실계좌 앱키 접촉 0 · 실계좌 토큰 무효(8005) 0 · 06:15 코어 실행에 준 영향 0 · 차단 장치 자체 시험 통과(5절).

### 3-4. 모의가 증명하지 못하는 것
- 모의 서버가 실서버와 같은 응답을 낸다는 보장이 없다. 가장 위험한 경로(주문 ID 없음에서 오는 중복, 응답 불명, 미체결 '있음')는 모의 통과만으로 증명되지 않는다(위원회 비판자·회의론자).
- 미체결 '있음'의 실계좌 응답은 1단계가 돌 때 C4로만 볼 수 있다(f-trading-infra-gap-review 20·56행). 그래서 T5 판단에는 모의 결과와 1단계 관측이 **둘 다** 필요하다.
- **2단계가 쓰는 종가(LOC) 주문은 모의로 시험할 수 없다.** 키움 답변(2026-11-17 13:44 KST, 10절)은 미국주식 모의투자가 '정규장의 지정가 주문만' 된다고 했다. - 가격 신호 자동 매도·감시 주문. 이 검토의 범위가 아니고 닫힌 질문이다(12절).

### 14-3. 길 셋

```
길 1 (권고)  모의 빼고 순서 그대로
[A 읽기 관측]  지금
      ↓
['켜' → 1단계 실적]
      │  그 사이 C2(호출 직렬화)를
      │  권한 자리 순번대로
      ↓
[T5 질문]  2단계를 열지
      ├─ 아니오 → 1단계 그대로
      └─ 예 → [제출 모듈 만들기]
                 ↓
              [보내지 않고 돌리기]
                 ↓
              [C 최소 수량 실주문]

길 2  길 1 + B를 T5 전에 미리 만들기
길 3  모의 시험 유지(안건 그대로, 키움 토큰 답 대기)
```

| 견줄 것 | 길 1 모의 빼고 순서 그대로 | 길 2 제출 연습 미리 | 길 3 모의 유지 |
|---|---|---|---|
| 지금 새 코드 | 없음 | 새 모듈 + 14-2의 넷 | 없음(착수 뒤 모의 모듈) |
| 권한 자리 | C2 1칸('켜' 뒤 순번대로) + T5 때 1칸 | C2·B 미리 + T5 때 1칸 | C2·모의 미리(3절은 착수 승인 1번으로 묶음) + T5 때 1칸 |
| 사장 손(T5 전) | C2 승인 1번 + 병합 | C2에 더해 위원회 읽기·착수 승인·병합 | 모의 계좌·앱키·착수·병합 2번 이상 |
| T5 전에 얻는 증거 | A | A + 드문 주문표의 연습 + 고장 연습(합성 시험과 같은 등급 — docs/future-order-readiness.md 5~9행 TESTED_ONLY) | A + 모의 서버 지정가 응답 |
| 종가 주문 실접수 확인 | T5 뒤 C | T5 뒤 C | T5 뒤 C |
| 바꾸는 규칙(T5 전) | 없음(C2는 원래 '켜' 뒤 — f-trading-infra-gap-review 54행) | 14-2의 넷 | 4절의 모의 예외 둘 |
| 남는 위험 | T5 뒤에 모듈이 처음 만들어진다(그래서 '보내지 않고 돌리기'를 먼저 둔다). T5 승인에서 첫 주문까지 제작·Judge·병합 기간이 그대로 든다 | 거짓 안심 · 권한 경로를 일찍 건드림 · T5가 '아니오'면 쓰지 않는 코드 | 토큰 영향 미확인 · 거짓 안심 |

- 시간: 길 2는 T5 승인 뒤의 모듈 제작 기간만큼은 줄일 수 있다(다시 만들 일이 없다면). 가장 긴 줄인 '켠 뒤 주문표 실적'은 어느 길에서도 줄지 않는다(0절). 그리고 권한·한도 변경은 한 번에 1건이라(CLAUDE.md 119행) B 차례가 T5 전에 온다는 보장이 없다(추정). 앞에 2027 달력과 정책 묶음 A가 있고(8절 3번) C2도 같은 자리를 쓴다. 순번을 사장이 바꾸면 달라진다.
- 길 1에서도 C2는 '켜' 뒤 권한 자리 순번대로 한다. 원래 계획 그대로이고(f-trading-infra-gap-review 54행 "승인 1번 + 병합"), 3절에서는 모의 착수 승인 1번이 C2를 덮었으므로(3-2절 M2 ①) 모의를 빼면 C2 승인을 따로 받는다. 같은 문서 66행의 나머지 선행 항목(iFixAi 감사 · 승인 채널 결정 · LOC 접수 마감 시각 확인)은 T5 전에 그대로 남는다.
- V3 순서로 본 판단: NO_CHANGE(길 3)는 막힌 질문 ㉥을 그대로 둔다 · REMOVE(길 1)는 ㉥과 사장 손을 없앤다 · REUSE는 길 1에서도 된다(주문표와 사장 실제 주문의 대조는 이미 돈다 — auto_core_tickets.py 631~679행, LOC 여부 664행) · ADD(길 2의 새 모듈)는 값이 작다.
- 길 1의 T5 뒤 순서('보내지 않고 돌리기' 다음 '최소 수량 실주문')는 초안이다. T5 때 사장이 정한다.

### 14-4. 길 1로 가면서 바뀐 줄 (2026-11-17 사장 결정 뒤 반영함)

- 머리 status·0절·3절·8절: 모의 주문 시험을 '하지 않음'으로 닫는다. 8절 선택지로는 (다)에 '모의는 쓰지 않는 쪽'을 더한 것이다. 착수 문구 `모의 주문 시험 착수 승인`은 쓰지 않는다.
- 4절: 모의 예외 두 줄이 필요 없어진다. 바뀌는 규칙이 없다.
- 2단계 선행 조건 목록의 '모의 N거래일 오류 0'(f-trading-infra-gap-review 66행)은 채울 수 없게 된다. 이 줄을 빼거나 다른 것으로 바꾸는 것은 T5 때 사장 결정이다. 바꾼다면 날 수가 아니라 '대조한 주문 n건 + 불일치 0'으로 세야 한다. 주문표가 없는 날은 불일치 0이 저절로 채워지기 때문이다.
- T5 때 정할 '모의 계정' 항목의 기본값("기본: 모의 가능하면 모의 먼저". f-trading-infra-gap-review 72행)이 '모의 없이 최소 수량 실주문' 쪽으로 기운다. system-evolution-2026-10-31.md 199행이 적어 둔 길이다("C6에서 미국주식 모의가 안 되면 … 최소 수량 실주문 2단계 … T5 질문 때 다시 고른다"). 이번은 '안 됨'이 아니라 '지정가만 됨'이라 그 문장이 그대로 적용되지는 않는다. 최종 선택은 여전히 T5 때다.
- 키움 추가 문의: 토큰 영향 질문은 모의를 쓰지 않으면 필요 없다. LOC 접수 시간은 사장 진술이 이미 있다("프리마켓 개장부터 정규장 마감까지", 2026-10-20 — auto_core_tickets.py 72~74행). 키움이 확인한 값은 아니어서 10절의 확인 필요는 그대로이고, 문의로 풀 수 있다.
- 11절 연결표: '확인 2건의 답'과 '모의 리허설 결과' 두 줄을 빼고 A 읽기 관측 줄을 더한다(아래 14-7).
- 함께 고칠 다른 줄: 2절 부품표의 C6 행과 '그 밖' 행 · 3-4절 끝줄 · 7절 판정의 권고 (나) · 10절 영향 ③ · 부록 문의 글(1·2번은 필요 없어지고 LOC 접수 시간 문의가 남는다). 안건 밖으로는 active-decisions.md intervene-1117 행(권고 (나)와 확인 2건을 적고 있다)과 짝 문서 order-stage3-design-memo-2026-11-17.md의 검토 완결 줄(미해결에 모의 2건을 적고 있다).

### 14-5. 한계

- 길 1은 실서버를 처음 만나는 일이 실돈 주문이 된다. 길 2·길 3도 종가 주문에서는 같다.
- 주문표가 드물다. 10/31 기준 실제 주문표는 1건이었다(system-evolution-2026-10-31.md 131행 · roadmap.md 27행. 지금 건수는 확인 필요). 그래서 주문표에 기대는 연습은 어느 길에서도 건수가 적다.
- A는 사장이 주문을 넣은 날에만 할 수 있다. 그 주문이 LOC가 아니면 LOC 모양은 못 본다. 주문 방식·수량·가격은 사장이 정하고 시스템은 권하지 않는다.
- HTS·MTS로 넣은 주문이 REST 미체결 조회에 잡히는지는 A로 처음 확인된다(확인 필요). 당일 주문·체결 조회(ust21150)에서 LOC 주문이 `Limit On Close`로 보이는 것은 이미 실측됐다(auto_core_tickets.py 70행, 2026-10-10).
- 길 2에서 승인 파일까지 연습하면 T5 결정 1번(승인 채널)의 (가)안을 가정하게 된다. (가)는 비교 시작점이지 기본값이 아니다(f-trading-infra-gap-review 71행). 그래서 B에서 승인 파일은 뺐다.
- 길 2의 착수 승인: Hard safety 문구(CLAUDE.md 19행)를 바꾸지 않으므로 규칙으로는 이 스레드가 그 제안에 올린 결정 카드 탭도 된다. 단 기록 4가지·바로 앞 제안·같은 날·1회일 때만이다(CLAUDE.md 72~78행 · active-decisions.md btn-approval 행. sc-1022 S4의 '주문 단계는 직접 입력'을 btn-approval이 착수에 한해 대체). 병합은 사장 PowerShell 한 줄이다. 머리 status와 13절의 '직접 입력으로만'은 3절 원안 기준이라 길 2를 고르면 함께 고친다.
