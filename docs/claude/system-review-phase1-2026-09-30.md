## 0. 결론

1. **목표는 맞았다. 문제는 판단 루프가 한 번도 끝까지 닫히지 않은 것이다.** "읽기 전용 의사결정 지원, 주문 권한 0, 데이터 없으면 멈춤" 원칙은 지켜졌다. 판단 기능도 계속 만들어졌다(9/29 커밋 `a5e872a`, +11,107줄). 그러나 수동 분석 20회를 보면 루프가 중간에서 끊긴다.
   - 16회는 키움 실데이터로 "브로커와 상태 파일이 다르다"(`broker_diff_status=DIFFERENT`)를 감지했다.
   - 그런데 조정은 한 번도 이뤄지지 않았다. 상태 파일은 여전히 8/12 기준이다.
   - 20회 모두 전체 보유 종목 분석(`full_holding_analysis_performed`)이 수행되지 않았다.
2. **8/24 이후 작업의 주력은 인증·거버넌스였다.** 추정 줄 수는 판단 약 14.2k, 거버넌스·키움 약 23.5k다. 이 거버넌스 작업은 데이터 결함을 실제로 잡기도 했다(부호 붙은 `cur_prc`, 미체결 API `return_code`). 비용이 과했던 곳은 따로 있다.
   - 코드 파일 해시 고정: Hot Path 파일을 고칠 때마다 K3가 된다.
   - 증거 사본: `activation` 폴더에 .py 사본 4,195개가 쌓였다.
   - CA K3: 9/28 하루에 후보 3건이 만들어졌지만 적용된 것은 없다.

   결국 "루프를 닫는 일"보다 "경로를 인증하는 일"이 먼저 진행됐다. 이는 프로젝트 지침 3절의 우선순위(의사결정 지원 > Hot-Path blocker > …)와 어긋난다.
3. **가장 큰 기회는 새로 만드는 것이 아니라 루프를 닫는 것이다.** 필요한 부품은 이미 저장소에 있다.
   - 수동 분석의 키움 조회 전용 경로
   - 조정 제안과 사용자 확인 적용 라이브러리
   - 결정 기록 검증기
   - 사후 성과 sidecar

   이 부품들을 "불일치 감지 → 조정 제안 → 사용자 확인 → 전체 보유 분석 → 결정 기록 → 사후 채점"으로 잇는다. 현황판은 이 루프의 **표시·알림 창**으로 쓴다. 현황판 db 값은 LLM이 기록한 표시용이므로 상태 입력으로 쓰지 않는다.
4. **Earnings archive는 증거가 아니라 리서치 단서다.** 출처가 대화 ID이고 원문 대조를 하지 않았다. 보유 종목과 직접 연결되는 것은 NBIS와 MRVL(MVLL의 기초자산)이다. 두 기업 모두 상세 요약이 없어서 원문 콜부터 읽어야 한다.
5. **안전 확인 1건.** 이 Cowork 세션에는 키움 주문 도구 2개(`kiwoom_order_submit`, `kiwoom_order_preview`)가 노출돼 있다. 현황판 예약 작업은 자동 승인 모드로 같은 키움 MCP를 쓴다. 저장소 문서에는 Codex 쪽 실행 MCP의 주문 gate가 꺼져 있다고 적혀 있지만, Claude 쪽 설정에도 같은 gate가 걸려 있는지는 확인 필요다(§5-3).
6. **사용자가 정해야 할 것:** 목표 우선순위, 방향 옵션, 보류 중인 K3 6~9단계 처리 방식(§7).

## 1. 재검토 프로세스 설계

### 1-1. 원칙

- **결정에서 거꾸로 설계한다.** 사용자가 실제로 내리는 결정에서 출발한다: 보유 종목별 ADD/HOLD/TRIM/EXIT, 현금 비교, 신규 후보 검토. 이 결정에 들어가지 않는 부품은 Cold Path로 분류한다.
- **루프 완결을 우선한다.** 새 기능보다 끊긴 연결(감지했지만 조정 안 됨, 조회했지만 분석 안 됨)을 먼저 잇는다.
- **위험에 비례해 검증한다.** 검증 강도는 "권한, 정책, 포트폴리오 상태, 판단에 쓰이는 데이터의 정확성"에 미치는 영향으로 정한다. 데이터 정확성 검증(가격 부호, 반환코드, 시간 무결성)은 유지한다. 코드 바이트와 provenance 인증은 범위를 다시 정한다.
- **지침 7절 순서를 따른다.** NO_CHANGE → REMOVE/SIMPLIFY → REUSE → REPLACE → ADD.
- **작게 나눠 되돌릴 수 있게 한다.** 단계마다 완료 조건과 중단 기준을 둔다.

### 1-2. 단계

| 단계 | 질문 | 산출물 | 작업 위치 | 통과 조건 |
|---|---|---|---|---|
| P0 목표·지표 | 무엇이 좋아지면 성공인가 | 지표표(§1-3)와 우선순위 | Cowork, 사용자 | 사용자가 우선순위를 결정 |

### 3-3. 방향 판정 (가설)

- 방향이 엉뚱한 목적으로 간 것은 아니다. 판단 기능, 데이터 검증, 인증이 **병행**됐다. 다만 **끝이 없는 루프**에 계속 부품을 더했다.
  - 감지는 됐지만 조정과 분석으로 이어지지 않았다.
  - 인증은 루프가 완성되기 전에 먼저 쌓였다.
- 현황판과 비교하면 이렇다. 저장소도 8/25부터 수동 실행 때 키움 실시간 잔고를 읽었다. 현황판이 다른 점은 두 가지다.
  - 매일 자동으로, 한 화면에 보여 준다.
  - 사용자가 부담 없이 본다.

  즉 전달 방식의 차이이고, 데이터 능력의 차이가 아니다. 반대로 현황판에는 저장소가 가진 데이터 검증 방어가 없다.
- 불일치를 조정하지 않은 이유는 "절차가 번거로웠음"이다(사용자 확인, 2026-09-30). 따라서 I0의 핵심은 새 기능이 아니라 확인 절차를 짧게 만드는 것이다.
- 남은 확인 사항: 수동 분석 결과를 실제 매매 판단에 어떻게 썼는지(사용자 확인 필요).

## 7. 목표 충돌과 사용자 결정 필요

### 7-1. 목표끼리의 충돌
