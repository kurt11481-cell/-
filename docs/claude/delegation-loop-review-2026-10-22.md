# AI 위임 루프 글 분석 → 투자_V2 뼈대 개편안 (2026-10-22)

## 0. 결론
1. **바꿀 뼈대는 "일 하나 = 플레이북(폴더) 하나"다.** 이점은 ① 규칙이 일마다 한 곳에만 산다 ② 지시문 속 스크립트를 파일로 빼서 AI가 매번 다시 적지 않는다(토큰·옮겨 적기 오류 감소) ③ 일마다 기계 검사가 붙는다 ④ 고친 것이 그 일의 notes.md로 모여 다음 판에 들어간다. **사장 승인 횟수는 줄지 않는다** — 해시 고정을 유지하는 한 내용을 바꿀 때마다 지시문(해시) 교체 승인이 필요하다(integrated-check-daily.txt 4행, 이미 파일+해시 방식인 주간 팀장회의도 10/19 하루 4번 교체 — README 53~56행).
2. **순서는 "정리 먼저, 최소안부터"다.** Vercel 원문의 단서: "This only worked because our semantic layer was already good documentation"(문서가 엉망이면 "더 빠른 나쁜 결과"). 우리 문서는 docs/claude 551개·11MB라, 플레이북을 지금 크게 늘리면 같은 규칙의 사본이 하나 더 생긴다. 그래서 ① 가장 작은 단계(지시문 속 스크립트를 파일로) ② 새로 만드는 예약 작업만 플레이북 형식 ③ 나머지 전환은 T4 문서 정리와 함께.
3. **새 에이전트를 늘리지 않는다.** 원출처(Anthropic 발표)의 핵심은 "범용 에이전트 1개 + 일별 스킬(폴더)"이다. 회사 조직(4팀·비서)은 에이전트가 아니라 플레이북 묶음으로 본다.
4. **사장 인터뷰로 사장의 업무 지식을 글로 받는다.** 지금 규칙은 대부분 AI 제안 → 사장 승인이다. 인터뷰 주제는 결과를 이미 아는 매매가 아니라 "카드를 '판단에 씀'으로 받는 기준" 같은 판단 기준으로 한다(사후 편향 방지). 결과는 규칙 후보(증거 강도 0)이고, 관문·한도를 바꾸거나 완화하는 후보는 K3(사장 승인 + 독립 Judge, Opus, 권한 변경 동시 1건)로만 간다.
5. **글의 외부 사례 숫자는 근거로 쓰지 않는다**(1절 A2).

## 3. 개편안 (NO_CHANGE → REMOVE/SIMPLIFY → REUSE → REPLACE → ADD)
- **NO_CHANGE**: 절대 안전경계·변경 등급·자동 코어·검토 안정성 V1~V5·주문 단계·해시 고정(지시문 교체 = 사장 승인). 플레이북은 이 위에 얹는 "일 매뉴얼" 층이고 권한을 바꾸지 않는다.
- **REMOVE/SIMPLIFY**
  - R1 지시문 속 스크립트를 파일로(자동 운영 코어 알림 read·host·core → 다음 후보 관심 명단 재채점). 팀장회의 방식 그대로: docs/claude/scheduled-prompts/<작업>/ 에 두고 지시문은 "받기 + 해시 확인 + 실행"만. **같음의 판정 = 지시문 안 스크립트 블록 원문(줄 끝 LF)의 sha256 = 새 파일의 sha256**. 같으면 의미가 같으므로 일반 변경, 한 글자라도 다르면 의미 변경 → 주문표 표시·입력 금지 판단이 걸려 있으므로 K3.
  - R2 "언제 쓰나"가 없는 문서는 플레이북이 아니라 기록 — T4의 archive 기준으로 넘김.
- **REUSE**: U1 "금지는 지시문, 본문은 해시 고정 파일, 불일치면 아무것도 안 함" 방식(통합 점검·팀장회의)을 표준으로. 통합 점검의 82KB 규칙 내용 자체는 표준이 아니다(T4에서 짧은 설명 작업으로 줄일 대상, automation-redesign:145). U2 팀장회의의 파일 받기. U3 이벤트 점검 --check-record 같은 기계 검사.
- **REPLACE**: 없음. T4의 정본 3개(SYSTEM 구조·규칙 · RUNBOOK 장애 대응 · DECISIONS 결정 기록)는 그대로 두고, 플레이북은 그 옆 "일 매뉴얼" 묶음으로 남는 4번째 정리 대상(T4 입력으로 전달).
- **ADD**
  - D1 플레이북 표준(새로 만드는 예약 작업부터): docs/claude/playbooks/<job>/ (T4의 docs/claude → archive/ 이동 대상에서 제외) — SKILL.md(목적 1줄 · 언제 쓰나 · 입력과 위치 · 번호 순서 · 결정 규칙 · 완료 정의 · 예외) + files/INDEX.md + checks.py(기계 검사, 모호한 품질어 금지) + notes.md(날짜·잘못·변경 1줄, 최신 위) + examples/(형식 예시만 — 매매 판단 예시는 넣지 않음). SKILL.md 300줄 이하. **로더는 플레이북이 읽거나 실행하는 파일 전부(SKILL.md·files/·checks.py)의 sha256 목록을 고정**한다 — 일부만 고정하면 나머지는 Cowork 수정 + 23:30 자동 커밋만으로 승인 없이 바뀐다. 고칠 때는 덮어쓰지 않고 판 번호 붙은 새 파일로(통합 점검 방식) — 덮어쓰면 해시 불일치로 교체 승인 전까지 그 작업이 멈추고 매도·위험 축소 알림도 같이 멈춘다.
  - D2 고침 루프: 결함·사장 지적은 그 일의 notes.md 1줄 + 가장 작은 수정(새 판 파일). 같은 실수 2번째 = 명시 금지 규칙. 해시 교체는 지금처럼 사장 승인.
  - D3 증명 실패: **지금 검증을 느슨하게 하지 않는다** — 하나라도 실패하면 지금처럼 막는다(매수 쪽 막힘, 매도·위험 축소 알림은 막지 않음). 실패해도 "실패 알림"은 보낸다. 2개 넘게 실패하면 원인이 된 단계를 함께 보고한다(글의 규칙 중 이 부분만 채택).
  - D4 예약 실행은 자기 플레이북을 고치지 않는다. 결과에 "개선 후보"만 적고 Cowork가 반영 → 해시 교체는 사장 승인.
  - D5 사장 인터뷰(일회성): 질문 1개씩 최소 8개, 사장이 끝났다고 할 때까지 파일을 쓰지 않음. 첫 주제 "카드를 '판단에 씀'으로 받는 기준". 결과 = docs/claude의 규칙 후보(증거 강도 0) → 리플레이 사전 등록 → 관문·한도 변경·완화는 K3.
  - D6 조직 원칙: "새 일 = 새 플레이북, 새 에이전트 아님". 팀 = 담당 플레이북 목록.

## 5. 위험과 막는 법
